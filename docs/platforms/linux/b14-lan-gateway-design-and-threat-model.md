# B-14 LAN gateway: proposed design and threat model

**Status (28 October 2026): design only.** No B-14 implementation, gateway test, installed outcome, or release claim exists. Implementation waits for accepted B-02 protected authority and filesystem39. The existing B-14 contract and A01–A10 matrix (archived: `docs/operations/linux-auto-configuration.md`) remain normative. B-03 installed routing and package evidence, then the applicable B-05/B-09 and independent release gates, remain dependencies. This document chooses a design to review; it grants no acceptance credit to B-02 or the older TPROXY gateway recipes.

## Scope and trust boundaries

An administrator opts in with explicit LAN interfaces and client source scopes. The ordinary AEGIS client remains local by default. The administrator supplies the normal user-owned relay/client configuration. There are no fleet addresses, implicit interface guesses, or public listener defaults. AP, DHCP, Wi-Fi admission and LAN physical security remain operator responsibilities; AEGIS owns only its declared gateway policy, forwarding verification, resolver binding, capture and rollback.

```
LAN client --[named LAN interface]--> ingress admission / persistent deny
         --[scoped transparent capture]--> AEGIS worker --[authenticated relay]--> WAN
                        DNS UDP/TCP --> LAN-bound resolver --> same worker/relay
         --[ordinary kernel FORWARD]--> DROP for both IP families, always
```

The kernel FORWARD path stays denied for every B-14 client packet, including `ESTABLISHED` conntrack entries. Captured traffic is handled as local delivery and emitted only as the client's authenticated relay connection from the gateway's OUTPUT path. A missing TPROXY/capture rule therefore falls into the deny path rather than ordinary routing or NAT. The design must prove that fragments, UDP, TCP, IPv4 and IPv6 cannot bypass capture through another hook, flowtable, hardware offload, bridge path, namespace or policy manager. Unsupported topology or family refuses admission; it never silently falls back to direct forwarding. No direct NAT/MASQUERADE rule is part of B-14 client egress.

The current `aegis-rpi-gateway.sh` and `RPI-GATEWAY.md` describe a legacy operator recipe that auto-detects interfaces and explicitly sends AP DNS/UDP directly. They do **not** satisfy B-14. The historical TPROXY warning also shows why an external interface cannot be selected for LAN capture: unsolicited WAN scans can become relay sessions. B-14 must have a separate opt-in configuration and independently tested policy; it cannot relabel that recipe as accepted gateway mode.

## Admission and configuration contract

1. Preflight validates a nonempty, explicit list of LAN interfaces and source CIDRs, a distinct uplink, declared IP families and transport support, relay pinning, native kernel capabilities, resolver binding and policy-manager compatibility. Empty, overlapping, WAN, loopback, relay-own, or ambiguous scopes refuse before changing network state. Name-only matching is insufficient: bind each admitted interface to its network namespace, ifindex, link identity and observed address/route generation. Refuse LAN or uplink enslavement, a shared bridge/bond/team/VRF master, macvlan/ipvlan on the uplink, an uplink VLAN without a separately reviewed tag boundary, and br_netfilter on an admitted LAN bridge. A LAN bridge master with isolated AP ports may be admitted only after its ports and uplink separation are sealed. Check netlink XDP, tc qdiscs/filters and TCX/netkit BPF attaches on every LAN device and uplink at admission and on drift; expand the BPF attachment bound to 3+N while retaining the global BPF-link refusal. Reuse, rename, removal, carrier replacement or namespace movement closes the gate and requires a new admission.
2. Classify every packet by ingress interface **and** source scope before capture. Reject WAN or unlisted ingress, source addresses outside the assigned LAN scope, source aliases of gateway/relay destinations, and packets with invalid IPv4/IPv6 headers or fragments that cannot be classified. A CIDR is not proof of individual client identity: hostile peers on the same LAN can spoof an allowed address or MAC. Deployment requiring per-device authorization needs an independently authenticated LAN (for example, AP/port admission); B-14 must state this limit and test out-of-scope spoofing. No resolver or transparent proxy socket is reachable from WAN or unlisted LAN paths.
3. Admit traffic only after B-02 authority, installed configuration, relay identity and fresh authenticated grant are proven. Apply the same generation and revocation to TCP sessions, UDP associations, DNS requests, queued work and replies. A stale worker, nonce, grant or interface generation cannot re-open an old packet path. The relay exception must be gateway-worker OUTPUT to a pinned endpoint only, never a broad forwarded-client exception. The present B-02 cgroup exception is cgroup-wide and does not by itself pin the output interface or destination; B-14 cannot activate on that schema.
4. DNS accepts both UDP/53 and TCP/53 on explicitly bound LAN addresses/scopes. It sends upstream through the authenticated tunnel, not a host resolver or plaintext uplink. Its cache, retries, truncation/TCP fallback and failure response must preserve the same grant and family gates. DNS is closed on WAN even if a service accidentally binds wildcard. Other client-chosen encrypted DNS is treated as ordinary tunneled TCP/UDP, not a claim that AEGIS controls its destination.
5. IPv4 and IPv6 are explicit capabilities. A build or host that lacks one family denies that family's forwarded and DNS traffic and advertises no support for it. If both are declared, acceptance proves each separately. IPv6 RA/ND and DHCP control-plane traffic must be scoped to the LAN and must not create a direct routed egress exception. The local-only INPUT class is DHCPv4 UDP/67, DHCPv6 fe80:: to ff02::1:2, and ICMPv6 RS/NS/NA with hoplimit 255 from :: or fe80:: on admitted LAN ifindexes. TPROXY matches only non-local unicast (`fib daddr type unicast`); all other broadcast/multicast is dropped, never relayed. Disable LAN accept_ra, autoconf and redirect acceptance; drop LAN RA/redirect types 134/137. DNS binds only admitted LAN addresses, never loopback or a wildcard with a WAN reachability gap.

## Sealed output and local delivery

B-14 requires a new, versioned sealed guard schema (v3) and exact foreign-policy verifier, followed by fresh B-02 acceptance; a second table cannot override B-02 output priority 10 or postrouting priority 110 drops. The v3 input records admitted LAN numeric ifindexes, source/destination scopes, families and the complete sealed relay endpoint pool, including every `configured_relay_pool` entry and `masque_server`. Its renderer and kernel readback must use the same exact `_expected` contract as B-02. B-14's owned TPROXY/mangle table joins `OWNED` with an exact verifier. A broad `oifname LAN accept` is forbidden. The only narrow LAN permits are SYN-ACK/RST/related ICMP bound to B-14 prerouting conntrack marks and an admitted LAN ifindex, hoplimit-255 link-local ND, and separately declared management. DNS and DHCP reply permits remain source/socket/port/grant scoped. TPROXY reply packets cannot depend on the current cgroup exception because a SYN-ACK request socket need not carry the worker cgroup.

B-14 installs owned OUTPUT and POSTROUTING deny chains before the B-02 priority-10/110 decision. For both families, packets toward an admitted LAN destination scope are dropped unless the numeric output ifindex equals the admitted LAN ifindex; a recreated device therefore stays closed until re-admitted. Worker-cgroup packets leaving via the uplink are dropped unless destination, protocol and port exactly match one sealed relay endpoint. No decrypted worker reply may use the WAN route. Install a high-metric unreachable route for every LAN scope in both families as an independent route fallback. A07 must delete the LAN interface during live TCP retransmission and UDP/DNS replies while an external WAN observer proves zero cleartext egress.

Kernel forwarding is always zero: `ip_forward`, every IPv4 per-interface forwarding knob, IPv6 `all.forwarding` and every available `force_forwarding`. TPROXY fwmark local delivery needs no IP forwarding. Admission and drift monitoring read and refuse any conflicting value; the B-14 journal never changes a forwarding knob. Keep `route_localnet=0` on all/default/uplink/LAN and reject non-loopback INPUT to 127.0.0.0/8 or ::1. Journal and monitor `rp_filter`, `accept_local`, `src_valid_mark`, `route_localnet` and the RA/redirect knobs. Do not carry over the legacy RPi gateway's `route_localnet=1`.

## Transaction and lifecycle

B-14 should be a separately named, versioned extension of the accepted B-02 install transaction, with a durable journal of intended/observed changes and owner tags for each nft object, route, policy rule, sysctl, DNS socket and service. It must not adopt an identically named foreign object. Baseline reads include both packet-policy families, all forwarding/route-localnet/RA/redirect knobs, route/rule state, LAN/uplink L2 and BPF attachments, other firewall managers and management reachability. Admission is invalid if the baseline cannot be read or a conflicting manager may erase the deny layer without a reliable handoff.

The proposed sequence is: (1) validate inputs and capture baseline; (2) install an early, durable **closed** ingress/FORWARD/OUTPUT/POSTROUTING deny generation while forwarding stays zero; (3) stage capture and LAN-only DNS while the worker gate remains closed; (4) verify exact kernel objects, hook priority, numeric interface identities, relay authority, unreachable LAN routes and independent negative controls; (5) enable the worker gate for the current grant generation. Every intermediate failure remains closed. Kernel rule updates should be atomic where the backend supports it, with a post-apply readback under the B-02 lock. Forwarding is never enabled. An absent or changed deny layer revokes the worker grant before any captured packet is accepted.

At reboot, an early boot unit must establish the deny layer before LAN interfaces can carry client traffic. The fwmark rule and local route must be owned networkd configuration or an exact verified networkd foreign-rule policy; UFW either has an exact tested integration or B-14 refuses admission while UFW is active. If host ordering cannot prove this, installation refuses gateway mode. Restart or upgrade keeps the old deny generation until the successor has revalidated policy, grant, route and sockets; it never relies on a user-space process surviving to block plain FORWARD. Worker death, tunnel/ACK loss, grant expiry/revocation, monitor loss, policy drift and interface churn close or retain the kernel gate and cancel active TCP/UDP/DNS work. Existing conntrack entries are not an allow rule; flush only B-14-owned entries if needed, without deleting unrelated state.

An **authorized opt-out** is a distinct transaction: close the gate, stop new captures and drain/cancel active work, verify no forwarded egress, then remove only journal-owned objects in reverse order and restore each baseline value by compare-and-swap. If a foreign actor changed an owned value, leave the safe deny state and report a conflict instead of blindly overwriting it. Unplanned failure must never run a broad cleanup that removes the kill-switch. Detached rollback and fresh management access checks are required for live trials; retained backup and receipts precede any removal. Preserve SSH and unrelated UFW/nft rules throughout.

## Threat model and proof obligations

| Threat or failure | Proposed control | Required negative evidence |
| --- | --- | --- |
| WAN scan or unlisted LAN client uses the relay as an open proxy/resolver | Explicit interface and source-scope admission before capture; LAN-bound DNS and INPUT guard; no auto-detected uplink | Send nonce traffic from WAN, wrong interface and wrong source scope; observe denial and no relay session |
| Direct TCP/UDP/DNS leak during startup, grant loss, worker death or missing capture | Persistent default-deny FORWARD and ingress guard for both families; worker generation gate; no client NAT fallback | Independent LAN/WAN captures and positive controls before, during and after each fault; no prohibited packet at WAN |
| Established conntrack, fragments, flowtable or offload bypasses revocation | Deny applies regardless of conntrack state; unsupported bypass mechanisms disabled or host refused | Keep established TCP/UDP/DNS open across revocation and policy churn; inject fragments; inspect effective hooks/counters |
| Interface replacement, ifindex reuse or route/policy churn changes scope | Bind interface and route generation; netlink invalidation and re-admission under authority lock | Remove/recreate/rename LAN device and change route while traffic runs; prove closed until fresh admission |
| Foreign firewall manager, partial apply or reboot removes the deny rule | Durable ownership and baseline journal, early boot deny, atomic apply/readback, policy drift monitor; fail closed on unverified policy | UFW/nft reload, injected partial writes, crash and reboot with independent early/late captures and post-boot readback |
| DNS recursion, cache/retry or resolver wildcard bind escapes tunnel | LAN-only listener plus kernel INPUT scope, tunnel-only upstream, grant-gated request/reply lifetime | UDP and TCP DNS positive; WAN/unlisted negatives; outage/retry and resolver death with capture |
| Malicious LAN peer exhausts relay or gateway resources | Bounded sessions, UDP association lifetime, DNS queue, per-scope rate limits and refusal counters | Saturation test shows no unbounded work, direct fallback or management starvation |
| Management lockout or unrelated policy/data loss | Narrow tagged objects, baseline compare-and-swap, detached rollback, fresh SSH, retained backups | Failure/opt-out leaves unrelated policy and management path intact; every failed attempt has a unique receipt |

A root administrator with arbitrary kernel-policy write access can remove any software guard; that actor is outside the enforcement boundary. A compromised LAN client, ordinary unprivileged local process, crashed AEGIS worker and competing policy manager are inside it. The implementation must make the exact trust boundary visible in operator documentation rather than claiming protection against root or a physically compromised gateway.

## Acceptance plan and release boundary

Use the existing stable B-14-A01–A10 IDs, without changing B-02 filesystem39 or borrowing its PASS. A01–A02 prove default-off admission, allowlisted client success, local-only DHCP/ND address acquisition, unauthorized/WAN/spoof refusal, L2 bridge bypass refusal, and zero relay traffic for broadcast/multicast. A03–A05 prove independent forwarded TCP, sustained UDP and DNS UDP/TCP on each declared family. A06–A07 inject authority, worker, interface and policy faults with already established flows, including deleted LAN ifindex during TCP retransmission and UDP/DNS replies, rogue LAN RA, and WAN-side cleartext capture. A08–A09 exercise fresh install, distinct-version upgrade, restart, reboot, partial apply, compensation and authorized opt-out. A10 binds independent review, exact source/package hashes, required completed CI, platform/family coverage and cleanup.

Each traffic case needs a disposable gateway, separate LAN client, controlled endpoint, unauthorized/WAN actor and observer outside the gateway; record nonce-bound payloads and synchronized LAN/WAN/relay captures, effective nft/route/sysctl/conntrack state, worker/grant generation and denial counters. Positive controls must show the observer and both IP families can see forbidden direct packets when deliberately generated outside the protected path; a zero-packet capture alone is not proof. Retain failed runs with unique names. The final source and installed package must match, and all leak checks keep their original refusal boundaries. No release claim follows from this design, filesystem tests, localhost echo or a cross-compiled binary.

Before implementation, prove the v3 guard and foreign verifier in a disposable kernel, the exact hook/priority and networkd/UFW coexistence that guarantee an early persistent deny, and a supported LAN topology with stable numeric identity through replacement and reboot. The existing scoped redirect must refuse the guard uplink and any default/relay-route interface in both Python and Rust validation; move fixture admission before `scoped_activate`, and remove preflight hints suggesting the default-route interface. If either cannot be demonstrated, refuse that topology instead of loosening the kill-switch.
