# Synthetic isolated relay rendering

`render_isolated_relay_canary.py` prepares a **second**, synthetic legacy relay
config bound to a currently free `127.0.0.1` port above 1023. It never launches a
server, installs a credential, changes a unit, opens TCP/443, or changes routes.
This only supports protocol/lifecycle rehearsal; it does not prove the public
relay-c route or client pool failover.

## Private input

Run the Linux CLI as root from a pinned source SHA using `/usr/bin/python3 -I
-S -B` and an absolute script path. Place a minimal synthetic candidate
generated by `prepare_relay_canary.py`, plus newly generated synthetic PEM
certificate and key, in root-owned 0700 parents as distinct regular 0600
files. No field other than `listen`, `cert`, `key`, `auth_token` and one
`[[legacy_auth_tokens]]` is accepted. Its original listen must already be
loopback. Never feed a deployed config or live TLS key into this tool. Pin the
candidate SHA externally. The helper rejects symlink, untrusted-owner or writable path
ancestors, extended Linux POSIX ACLs, unsafe file modes, expired credentials,
an occupied port, and an existing output directory.

Run `render` with absolute `--candidate`, `--cert`, `--key`, `--out-dir`,
`--port` and `--expected-candidate-sha256`. Keep the output parent root-owned
0700. The output contains `config.toml`, `cert.pem`, `key.pem` and
`manifest.json` with mode 0600. The manifest contains only hashes, device and
inode pins, port and `launched=false`. The preparation-time bind probe is not
a reservation; independently recheck ownership and socket availability
immediately before any separately reviewed launch.

## Validation and cleanup

Validate `config.toml` using the exact signed server binary in `config-check`
mode. That validation does not start a listener. Preserve only exit status,
counts, artifact hashes and binary identity in the receipt. A future launched
canary needs a separate controller that owns its PID/start marker, namespace,
listener, certificate custody, timeout and independent cleanup witness.

`cleanup --out-dir ... --expected-manifest-sha256 ... --never-launched` is only
for rendered material that has **never** been given to a running server. It
checks the exact directory/file inodes and digests, requires a free loopback
port, refuses unexpected files and (on Linux) scans `/proc` for open files or
working directories referencing the output. It does not stop processes.
After a launch, this command is not an accepted rollback; stop and verify the
exact process and namespace through the independent controller first, then
apply a separately reviewed cleanup procedure. If cleanup refuses or partially
fails, preserve the directory and receipt for incident analysis. Do not retry
blindly or unlink files referenced by an active process.

For public relay-c failover, identify and control the current edge/DNS route,
TLS trust, firewall and client pool, then demonstrate authenticated traffic
and exact route inverse with a separate health witness. A loopback-only PASS
does not permit a live legacy credential, r77 sidecar `--apply`, or closure of
finding 14.
